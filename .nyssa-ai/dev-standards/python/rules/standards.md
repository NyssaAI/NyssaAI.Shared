# Python development rules

> [!IMPORTANT] Scope Directive
> Defines the mandatory architectural rules, multi-platform portability, Functional Core domain modeling, workflow orchestration, explicit persistence, single-responsibility headers, ASCII interface trees, strict type safety, operational logging, and testing contracts for Python development in owned repositories. It inherits the [cross-language architectural rules](architecture-standards.md) and [common repository organization rules](repo-standards.md), governing feature-first `snake_case` modules, frozen dataclasses, discriminated-union results, and explicit test isolation; it does NOT prescribe generic language tutorials or dictate external third-party library internals.

- **PY-FILE:** One primary concept/type or workflow function per module (`snake_case.py`), named after its primary export (`EmailAddress` in `email_address.py`, `register_email` in `register_email.py`, `email_formatter_json` in `email_formatter_json.py`). Keep a concept's construction functions, methods, and same-concept discriminated-union arms with it. Simple, pure feature-owned DTOs, data contracts, enums, and `NewType` identifiers without behavioral methods may be grouped in a feature's `types.py` file; unrelated behavioral classes, `Protocol` contracts, or workflow functions require separate files. Package `__init__.py` files either remain empty or expose explicit boundary APIs. Source files over 100 lines are discouraged (inspect files between 101 and 350 lines for mixed responsibilities), and files over 350 lines are prohibited.
- **PY-HEADER:** Every authored Python file begins with `# Responsibility: <summary>` stating its Single Responsibility, followed by `# Public interface:` and a literal ASCII tree (`# +-- ` / `# `-- `) of the public interface it exposes. Include public classes, protocols, functions, constants, type aliases, and public class fields/methods/properties (using `new(...)` for `__init__` and parameter names omitting `self`/`cls` for callables). Omit private implementation details (`_`-prefixed names); explicitly write `# (none)` when nothing is exported. Keep the tree synchronized with code. Optional shebang lines may precede the header.
- **PY-STRUCTURE:** Follow the [common repository organization rules](repo-standards.md) (`REPO-ROOT`, `REPO-SCRATCH`, `REPO-CONFIG`, `REPO-DOCS`, `REPO-GOVERNANCE`, `REPO-TEST-LAYOUT`) and [cross-language architectural rules](architecture-standards.md). Organize production source under `src/` as a Feature-First Modular Monolith by feature, initially flat, with `snake_case` package folders, and isolate tests under `test/unit/` and `test/use_case/` without co-mingling `test_*.py` or `*_test.py` files in `src/`. Add progressive Hexagonal (`domain`, `application`, `infrastructure`, `api`, `ui`) layers inside a feature only when earned by complexity or multi-platform adapters, and use `.temp/` for local scratch and cache outputs. No `contracts`, `shared`, `utils`, `helpers`, `common`, `misc`, `types` or `models` catch-all folders (a feature-local `types.py` file for pure DTOs is permitted, never a `types/` directory), and no `tmp`, `temp` or `scratch` folders.
- **PY-BOUNDARY:** `domain` and `application` modules do not import `infrastructure`, `configuration`, `api`, or `ui` modules, and `domain` does not import `application`. Consumers own narrow collaborator contracts (`typing.Protocol`). Keep adapter implementations private to their feature; public provider contracts and required public data live at feature roots. A consumed package exposes a covering protocol when needed; data-only capabilities need no empty protocol.
- **PY-PORTABILITY:** Keep `domain` and `application` modules 100% OS- and platform-agnostic. Isolate OS-specific paths, POSIX/Windows process semantics, native bindings, and UI/transport mechanics behind narrow feature-owned `Protocol` ports implemented in `infrastructure`, `api`, or `ui`. Wire dependencies explicitly at the composition root; ban import-time auto-discovery, dynamic module scanning (`importlib` plugin scanning in business layers), monkey-patching, and service locators.
- **PY-NAME:** Entity-first names (`UserRepositoryPostgres`, `email_formatter_json`, `email_formatter_text`). Behavioral contracts (`typing.Protocol`) use `PascalCase` role names without an `I` prefix (`EmailFormatter`, not `IEmailFormatter`; only C# uses the `IInterface` convention). Classes, protocols, type aliases, and `NewType` identifiers use `PascalCase`, functions/methods/variables/modules use `snake_case`, module constants use `SCREAMING_SNAKE_CASE`, and booleans use assertion-like names (`is_valid`, `has_permission`).
- **PY-DATA:** Model domain values and DTOs as immutable dataclasses (`@dataclass(frozen=True, slots=True)`) or validated frozen boundary models (such as frozen Pydantic models at external delivery/configuration boundaries). Use `typing.NewType` or frozen value wrappers for distinct domain identifiers, immutable collections (`tuple`, `frozenset`, `Mapping`), and `Literal` or `StrEnum` / `Enum` for closed sets. Validate untrusted external data (`object` / raw dicts) through named parser functions; `typing.cast` does not establish validity. Create new values instead of mutating existing ones, and keep I/O and orchestration out of data types.
- **PY-DOMAIN:** Follow Functional Core / Imperative Shell domain modeling: represent domain entities and state as `@dataclass(frozen=True, slots=True)` records and express business rules and state transitions as pure functions or methods returning `Result[T, E]` containing a new frozen instance (`dataclasses.replace(self, ...)` or explicit construction)—never mutating state in-place, performing I/O, or logging inside domain types. Action-taking handlers or services load state via narrow repository `Protocol` ports, invoke the pure transition, and persist the new record. Trivial pass-through CRUD workflows without domain invariants may operate directly on frozen DTOs in the handler/service. **Active Record** (Django/SQLAlchemy ORM models with `.save()` / `.delete()` or lazy-loaded relation attributes used as domain objects) is strictly prohibited.
- **PY-WORKFLOW:** Separate command workflows (validate, transition state, persist, and return `Result[T, E]`) from query workflows (Pragmatic CQS / Lightweight CQRS, reading directly into frozen projection DTOs when read shapes diverge from write models). Use tiered dispatch: direct constructor-injected service/handler calls for simple components or libraries, and an explicitly registered, type-safe Command/Query Bus (explicit handler registration with pipeline middleware for logging/telemetry; no runtime module scanning) for application workflows. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) must use explicit `__init__` Dependency Injection and inject a structured logger; pure value/DTO dataclasses remain dependency-free and logger-free. Default to current-state persistence (with explicit audit/outbox tables when needed), reserving Event Sourcing strictly for domains with an explicit ledger or replay requirement.
- **PY-PERSISTENCE:** Implement data access through explicit parameterized SQL (`psycopg`, `asyncpg`, `sqlite3`) or explicit SQLAlchemy Core query builders with explicit row mapping into frozen dataclasses. Ban Active Record, ORM lazy-loading proxies, implicit session dirty-tracking across layers, and dynamic attribute mappers. Never leak `AsyncSession`, `Session`, database connections, or cursors outside `infrastructure` adapters; command workflows own transaction boundaries explicitly. Manage schema changes exclusively through versioned, deterministic SQL migration files executed in production and in `test/use_case/` fixtures; ban runtime schema auto-generation (`Base.metadata.create_all()` in production workflows).
- **PY-STRICT:** Configure project metadata and tooling in `pyproject.toml` (managed with `uv` or standard PEP 621 locks), lint and format with `ruff`, and enforce strict static type checking (`mypy --strict` or `pyright` strict mode). Annotate all function and method parameters and return types. `Any` is forbidden in owned code; accept `object` at untrusted boundaries and narrow with `isinstance` or structural checks. Do not silence type errors with unreasoned `# type: ignore`.
- **PY-FAILURE:** Expected domain and operational failures return a discriminated-union `Result[T, E] = Ok[T] | Err[E]` (frozen dataclasses with `ok: Literal[True]` and `ok: Literal[False]`). Translate expected dependency exceptions at narrow adapter boundaries while preserving internal causes (`cause: BaseException | None`) and redacting sensitive details. Propagate `asyncio.CancelledError`, `KeyboardInterrupt`, and `SystemExit` rather than swallowing them into domain results. Reserve raised exceptions (`ValueError`, `RuntimeError`) for programmer errors and startup/construction invariant violations. PY-LOG defines diagnostic ownership.
- **PY-LOG:** Robust logging is mandatory at owned operational boundaries. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) injects a structured logger via constructor DI, emitting `Info`/`Warn`/`Error` for operational boundary outcomes and `Debug`-level step telemetry (routed to diagnostic sinks such as Sentry or PostHog when debug mode is enabled). Emit structured, correlated outcomes with operation, severity, elapsed duration (measured with `time.monotonic()`), safe diagnostic causes, and deployed version. Expose actionable degradation before failure, including relevant retries, latency, and fallback use. Assign one owner to each terminal outcome; keep pure domain logic and frozen DTOs quiet. Exclude secrets and sensitive payloads, bound logging cost, and contain sink failures without changing business results. Test emitted records and document how they support detection, diagnosis, and verification of a fix. Follow the [logging contract](../references/python/logging.md); a logger call alone is not conformance.
- **PY-LIFETIME:** Inject storage, transport, clock/time, randomness, and loggers through constructors (for action-taking classes) or parameters. Avoid mutable module singletons, service locators, mutable default arguments, and import-time I/O. Manage owned resources deterministically with context managers (`with` / `async with`); never close a borrowed resource supplied by a caller.
- **PY-DOC:** Document public classes, protocols, functions, and methods with concise docstrings describing behavior, preconditions, failure codes, cancellation, and ownership contracts; top-of-file ASCII headers complement these docstrings.
- **PY-TEST:** Use `pytest` (or `unittest` for zero-dependency stdlib runners) with `test_<subject>_<scenario>_<expected>` names and `@pytest.mark.parametrize` for multiple examples of one behavior. Maintain fast `test/unit/` tests and complete public `test/use_case/` workflows using real Docker-hosted dependencies for infrastructure-backed behavior. Tests are executable documentation: use the simplest idiomatic style, direct setup/actions/assertions, and only patterns justified by a concrete need (KISS). Hide infrastructure lifecycle in fixtures while keeping public usage and business expectations visible. Follow the [testing contract](../references/python/testing.md), including isolation, cleanup, logging evidence, and explicit local execution; passing syntax checks or starting a container is insufficient.

- **PY-REVIEW:** Use the [code-smell and anti-pattern catalog](../references/python/code-smells.md) for relevant changed code and tests. Distinguish explicit rule violations from smells needing investigation. Every finding needs source evidence, an applicable rule or demonstrated problem, a concrete consequence, and the smallest correction. Preserve justified patterns and simple code; do not refactor from names, line counts, or smell labels alone.

## Design decisions (review required)

- **SOLID-S:** Give each component one coherent responsibility. Separate business policy from delivery and infrastructure when their reasons for changing differ.
- **SOLID-O:** Extend established variation through another implementation without changing the stable workflow. Introduce a seam only for real variation, external I/O, or an actual consumer boundary.
- **SOLID-L:** Every implementation honors the complete contract, including failure, ownership, cancellation and side effects. Run the same behavioral contract against interchangeable implementations.
- **SOLID-I:** Keep contracts specific to their consumers. No dummy operations, fabricated success, silent no-ops or unsupported members.
- **SOLID-D:** Core policy owns its collaborator abstractions. Adapters implement them; composition supplies implementations. Keep vendor, transport and persistence types outside core contracts.
- **REPO-FEATURES:** Prefer aligning feature folders under `src/` (and mirrored suites under `test/unit/` and `test/use_case/`) with cohesive `plan-product` Feature Groups (`F-gg` in `docs/features.md`) or domain concepts (`C-nn` in `docs/concepts/`) rather than creating a separate top-level folder per individual `F-gg.nn` feature number. Keep subordinate features within their owning feature-group folder, starting flat.
- Use dependency injection, repository, adapter, strategy, decorator, factory, builder, observer or covering protocol only when the task justifies that particular pattern. A simple change can need no new pattern.
- Make resource ownership explicit. A component disposes what it owns, never what it borrows. Inject time, randomness and external systems when core behavior depends on them.
- Prefer JSON-RPC 2.0 over HTTPS for new request/response network APIs unless explicit compatibility requirements dictate otherwise. Keep protocol handling separate from business invariants; check those invariants for non-network callers too.

## Observable examples and tests

Samples must run, expose actual results, show a meaningful expected failure, and test those observations through the public surface. A compiling or type-checked example is not proof of behavior. Explain why the design applies and when a simpler design is enough. Keep tests deterministic and resources isolated. Integration tests must exercise the technologies actually claimed; an in-memory provider does not prove database persistence. Library tutorial tests show public setup and the complete caller workflow, with one visible Arrange / Act / Assert sequence. Contract tests must exercise every interchangeable implementation.

## Scope and precedence

Explicit user and repository requirements take precedence. Record an exception with its scope and reason; do not silently disable a check. Apply rules to owned code; respect upstream compatibility and generated-code conventions. These are Jeremy Maynor's preferences, not claims of universal language practice. A passing check covers only the checks listed in the package README. SOLID judgment, useful comments, conceptual cohesion and full correctness still require review.
