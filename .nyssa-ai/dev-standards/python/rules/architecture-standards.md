# Cross-language architectural rules

> [!IMPORTANT] Scope Directive
> Defines the mandatory language-agnostic software architecture, domain modeling, workflow orchestration, persistence mapping, multi-platform/AOT portability, file cohesion, public-surface header, dependency boundary, naming, immutability, explicit failure, operational logging, and two-tier testing rules across all owned repositories. Every language rulebook ([`csharp-standards.md`](csharp-standards.md), [`go-standards.md`](go-standards.md), [`python-standards.md`](python-standards.md), and [`typescript-standards.md`](typescript-standards.md)) inherits these architectural invariants and specifies language-idiomatic syntax, tooling, and checker rules.

- **ARCH-FILE:** Place one primary concept, behavioral class, protocol/interface, or workflow function per file, named after that primary export in the language's file-naming convention. Keep a concept's constructors, methods, and tightly coupled error/result helpers in the same file. Component props (`<Component>Props` in TSX) describe the same concept and may stay beside the component. In Python (`types.py`) and TypeScript (`Types.ts` or `types.ts`), simple feature-owned DTOs, data contracts, enums, and branded/typed identifiers without behavioral methods may be grouped in a feature's dedicated types file; in C#, grouping simple same-namespace DTOs or enums requires an explicit `grouped-dtos.json` entry. Unrelated behavioral classes, protocols/interfaces, or workflow functions always require separate files. Keep source files concise: files over 100 lines are discouraged (inspect files between 101 and 350 lines for mixed responsibilities), and files over 350 lines are prohibited and must be decomposed along cohesive responsibility boundaries.
- **ARCH-HEADER:** Every authored source file in languages with explicit public-surface headers (Python, TypeScript/TSX, Go) begins with a comment stating its Single Responsibility (`Responsibility: <summary>`), followed by `Public interface:` and a literal ASCII tree (`+-- ` / `` `-- ``) of the public interface it exposes. Include exported types, functions, constants, and public members with parameter names for callable entries. Omit private implementation details and write `(none)` when nothing is exported. Keep the tree synchronized with code. (C# uses compiler-enforced XML documentation comments instead of an ASCII header tree.)
- **ARCH-STRUCTURE:** Follow the [common repository organization rules](repo-standards.md) (`REPO-ROOT`, `REPO-SCRATCH`, `REPO-CONFIG`, `REPO-DOCS`, `REPO-GOVERNANCE`, `REPO-TEST-LAYOUT`, `REPO-FEATURES`). Organize production source under `src/` as a Feature-First Modular Monolith by cohesive feature or Feature Group (`F-gg`), initially flat, and isolate automated tests under `test/unit/` and `test/use_case/` without co-mingling test files in `src/`. Add progressive Hexagonal (Ports & Adapters) layers (`domain`, `application`, `infrastructure`, `api`, `ui` — or `PascalCase` in C#) inside a feature only when earned by complexity or multi-platform adapters. Use `.temp/` for all local scratch and build-staging outputs. Never create catch-all folders (`contracts`, `shared`, `utils`, `helpers`, `common`, `misc`, `types`, `models`) or ad-hoc scratch folders (`tmp`, `temp`, `scratch`, `.scratch`); a feature-local `types.py` or `Types.ts`/`types.ts` *file* for pure DTOs is permitted in Python and TypeScript, whereas a `types/` *directory* remains prohibited.
- **ARCH-BOUNDARY:** Dependencies point strictly inward: `domain` never imports `application`, `infrastructure`, `configuration`, `api`, or `ui`; `application` never imports `infrastructure`, `configuration`, `api`, or `ui`. Consumers own narrow collaborator contracts (interfaces/protocols). Keep adapter implementations private to their feature; public provider contracts and required public data live at feature roots. A consumed library or package exposes a covering interface when needed for caller workflows; data-only capabilities need no empty interface.
- **ARCH-PORTABILITY:** Keep `domain` and `application` layers 100% OS- and platform-agnostic. Isolate OS-specific file paths, native APIs, process signaling, keychain/registry access, and UI/transport mechanics behind narrow feature-owned port interfaces implemented in `infrastructure`, `api`, or `ui`. Wire dependencies explicitly at the composition root (or via compile-time DI source generators); ban runtime assembly scanning, reflection-based auto-registration, dynamic proxy generation, and service locators. All C# code must remain Native AOT and trim-compatible.
- **ARCH-NAME:** Use entity-first names across all languages (for example, `UserRepositoryPostgres`, `EmailFormatterJson`, `EmailFormatterText`) so related implementations group by domain concept first, followed by specialization. Use assertion-like boolean names (`isValid` / `is_valid`, `hasPermission` / `has_permission`). Only C# (`CS-NAME`) uses the `I`-prefix convention for interfaces (`IEmailFormatter`); Python (`Protocol`), TypeScript (`interface`), and Go (`interface`) name behavioral contracts directly after the role or capability (`EmailFormatter`) without an `I` prefix.
- **ARCH-DATA:** Model domain values and DTOs as immutable data structures (`@dataclass(frozen=True, slots=True)` in Python, `readonly` interfaces/tuples in TypeScript, expanded-body `record` in C#, value structs with unexported fields in Go). Use distinct typed/branded domain identifiers rather than raw primitives where identifiers can be confused. Validate untrusted external data at boundaries through named parsers or constructors; type casts or annotations alone do not establish runtime validity. Create new values instead of mutating existing ones, and keep I/O and orchestration out of data types.
- **ARCH-DOMAIN:** Follow Functional Core / Imperative Shell domain modeling: represent domain entities and state as immutable records/values and express business rules and state transitions as pure functions or methods on the domain concept that return `Result<T>` (`(T, error)` in Go) containing a new immutable instance—never mutating entity state in-place, performing I/O, or logging inside domain types. Action-taking handlers or services load state through narrow repository ports, invoke the pure transition, and persist the new state. Trivial pass-through CRUD workflows without domain invariants may operate directly on immutable DTOs in the handler/service. **Active Record** (domain objects holding database connections/sessions or exposing `.Save()`, `.Update()`, or `.Delete()` persistence methods) is strictly prohibited.
- **ARCH-WORKFLOW:** Separate command workflows (validate, transition state, persist, and return `Result`) from query workflows (Pragmatic CQS / Lightweight CQRS, reading directly into immutable projection DTOs when read shapes diverge from write models). Use tiered dispatch: direct constructor-injected service/handler calls for simple components or libraries, and an AOT-safe, explicitly registered Command/Query Bus (static generic dispatch with pipeline middleware for logging/telemetry; no runtime reflection or assembly scanning) for application workflows. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) must use constructor Dependency Injection and inject a structured Logger; pure value/DTO types remain dependency-free and logger-free. Default to current-state persistence (with explicit audit/outbox tables when needed), reserving Event Sourcing strictly for domains with an explicit ledger or replay requirement.
- **ARCH-PERSISTENCE:** Implement data access through explicit SQL or type-safe query builders with explicit or compile-time AOT-safe mapping into immutable records/DTOs. Ban Active Record, lazy-loading proxies, implicit dirty-tracking side effects, and runtime reflection object mappers. Never leak `IQueryable`, `DbContext`, ORM sessions, or database cursors outside `infrastructure` adapters; command workflows own transaction boundaries explicitly. Manage schema changes exclusively through versioned, deterministic SQL migration files executed in production and in `test/use_case/` fixtures; ban runtime schema auto-generation (`EnsureCreated`, `synchronize: true`, `create_all`).
- **ARCH-STRICT:** Enable mandatory static type-checking and compiler safeguards in every owned project (`mypy --strict` or `pyright` strict mode + `ruff` in Python; `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `verbatimModuleSyntax` in TypeScript; `Nullable` and warnings-as-errors in C#; `gofmt` and `go vet` in Go). Never use untyped escape hatches (`Any` in Python, `any` in TypeScript) or silently suppress checks to reduce error counts; narrow `object` / `unknown` at boundaries.
- **ARCH-FAILURE:** Represent expected domain and operational failures as explicit return values (`Result[T, E]` discriminated union in Python, `Result<T>` discriminated union in TypeScript, `Nyssa.Results.Result<T>` in C#, `(T, error)` in Go) rather than throwing exceptions for normal control flow. Translate third-party dependency failures at narrow adapter boundaries while preserving internal causes and redacting sensitive details. Propagate cancellation (`asyncio.CancelledError`, `CancellationToken`, `AbortSignal`, `context.Context`) cleanly rather than swallowing it as a domain validation failure. Reserve uncaught exceptions or panics for programmer errors and fatal process conditions.
- **ARCH-LOG:** Robust operational logging is mandatory at owned operational boundaries. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) injects a structured logger via constructor DI, emitting `Info`/`Warn`/`Error` for operational boundary outcomes and `Debug`-level step telemetry (routed to diagnostic sinks such as Sentry or PostHog when debug mode is enabled). Emit structured, correlated outcomes with operation, severity, elapsed duration (measured with a monotonic clock), safe diagnostic causes, and deployed version. Expose actionable degradation before failure (retries, slow dependencies, fallback use). Assign one owner to each terminal outcome; keep pure domain logic and DTOs quiet. Exclude secrets and sensitive payloads, bound logging cost, and contain diagnostic sink failures without changing business results. Test emitted records and document how they support detection, diagnosis, and verification of a fix.
- **ARCH-LIFETIME:** Inject storage, transport, clock/time, randomness, and loggers explicitly through constructors (for action-taking classes), parameters, or composition roots. Avoid mutable module singletons, service locators, and import-time side effects. Make resource ownership explicit: a component disposes or closes what it owns and never disposes what it borrows.
- **ARCH-DOC:** Document exported types, protocols/interfaces, functions, and methods with concise docstrings/comments covering behavior, preconditions, failure contracts, cancellation, and resource ownership.
- **ARCH-TEST:** Maintain fast, deterministic unit tests under `test/unit/` (requiring no Docker, network services, or browser), complete public use-case tests under `test/use_case/` (exercising real caller workflows and disposable Docker-hosted or local dependencies for infrastructure-backed behavior), and optional full-stack browser/system end-to-end tests under `test/e2e/` (such as Playwright driving a real browser against the running application). Name tests by subject, scenario, and expected outcome (`test_<subject>_<scenario>_<expected>` or `<Subject>_<Scenario>_<Expected>`). Tests are executable documentation: use the simplest idiomatic style (KISS), keep one visible Arrange / Act / Assert sequence per test, keep business setup and assertions visible in the test body, and hide infrastructure provisioning and teardown in fixtures.
- **ARCH-REVIEW:** Distinguish explicit rule violations from code smells needing investigation. Every review finding requires a source location, observed evidence, an applicable rule or demonstrated problem, a concrete consequence, and the smallest correction. Preserve justified patterns and simple code; never refactor from names, line counts, or smell labels alone.

## Design decisions (review required)

- **SOLID-S:** Give each component one coherent responsibility. Separate business policy from delivery and infrastructure when their reasons for changing differ.
- **SOLID-O:** Extend established variation through another implementation without changing the stable workflow. Introduce a seam only for real variation, external I/O, or an actual consumer boundary.
- **SOLID-L:** Every implementation honors the complete contract, including failure, ownership, cancellation and side effects. Run the same behavioral contract against interchangeable implementations.
- **SOLID-I:** Keep contracts specific to their consumers. No dummy operations, fabricated success, silent no-ops or unsupported members.
- **SOLID-D:** Core policy owns its collaborator abstractions. Adapters implement them; composition supplies implementations. Keep vendor, transport and persistence types outside core contracts.
- **REPO-FEATURES:** Prefer aligning feature folders under `src/` (and mirrored suites under `test/unit/` and `test/use_case/`) with cohesive `plan-product` Feature Groups (`F-gg` in `docs/features.md`) or domain concepts (`C-nn` in `docs/concepts/`) rather than creating a separate top-level folder per individual `F-gg.nn` feature number. Keep subordinate features within their owning feature-group folder, starting flat.
- Use dependency injection, repository, adapter, strategy, decorator, factory, builder, observer or covering interface only when the task justifies that particular pattern. A simple change can need no new pattern.
- Make resource ownership explicit. A component disposes what it owns, never what it borrows. Inject time, randomness and external systems when core behavior depends on them.
- Prefer JSON-RPC 2.0 over HTTPS for new request/response network APIs unless explicit compatibility requirements dictate otherwise. Keep protocol handling separate from business invariants; check those invariants for non-network callers too.

## Language rulebook mapping

| Architectural Rule | C# / .NET ([`csharp-standards.md`](csharp-standards.md)) | Go ([`go-standards.md`](go-standards.md)) | Python ([`python-standards.md`](python-standards.md)) | TypeScript / React ([`typescript-standards.md`](typescript-standards.md)) |
| :--- | :--- | :--- | :--- | :--- |
| **ARCH-FILE** | `CS-FILE` (`PascalCase.cs`; `grouped-dtos.json` for simple DTOs) | `GO-FILE` (`PascalCase.go` / primary export) | `PY-FILE` (`snake_case.py`; `types.py` for pure DTOs) | `TS-FILE` (`PascalCase.ts`/`.tsx` or `camelCase.ts`; `Types.ts`/`types.ts` for pure DTOs) |
| **ARCH-HEADER** | `CS-DOC` (XML doc diagnostics; no ASCII header tree) | `GO-HEADER` (`// Responsibility:` + ASCII tree) | `PY-HEADER` (`# Responsibility:` + ASCII tree) | `TS-HEADER` (`// Responsibility:` + ASCII tree) |
| **ARCH-STRUCTURE** | `CS-STRUCTURE` (`PascalCase` folders & `.csproj`) | `GO-STRUCTURE` (`camelCase` packages, `cmd/`, `internal/`) | `PY-STRUCTURE` (`snake_case` packages, `pyproject.toml`) | `TS-STRUCTURE` (`camelCase` folders, explicit entrypoints) |
| **ARCH-BOUNDARY** | `CS-BOUNDARY` | `GO-BOUNDARY` | `PY-BOUNDARY` | `TS-BOUNDARY` |
| **ARCH-PORTABILITY** | `CS-PORTABILITY` (Native AOT, no runtime reflection/scanning) | `GO-PORTABILITY` (OS-agnostic core, explicit wiring) | `PY-PORTABILITY` (OS-agnostic core, explicit wiring) | `TS-PORTABILITY` (runtime-agnostic core, explicit wiring) |
| **ARCH-NAME** | `CS-NAME` (entity-first; `IInterface` required) | `GO-NAME` (entity-first; no `I` prefix) | `PY-NAME` (entity-first; `Protocol` without `I` prefix) | `TS-NAME` (entity-first; `interface` without `I` prefix) |
| **ARCH-DATA** | `CS-DATA` (expanded-body `record`, `required`/`init`) | `GO-DATA` (immutable value structs, defined ID types) | `PY-DATA` (`@dataclass(frozen=True, slots=True)`, `NewType`) | `TS-DATA` (`readonly` interfaces, branded IDs) |
| **ARCH-DOMAIN** | `CS-DOMAIN` (Functional Core records + pure transitions; no Active Record) | `GO-DOMAIN` (value transitions returning `(T, error)`; no Active Record) | `PY-DOMAIN` (frozen dataclass transitions returning `Result`; no Active Record) | `TS-DOMAIN` (immutable transitions returning `Result`; no Active Record) |
| **ARCH-WORKFLOW** | `CS-WORKFLOW` (Pragmatic CQS, AOT bus/handlers, constructor DI + logger) | `GO-WORKFLOW` (Pragmatic CQS, explicit handlers/bus, constructor DI + logger) | `PY-WORKFLOW` (Pragmatic CQS, explicit handlers/bus, constructor DI + logger) | `TS-WORKFLOW` (Pragmatic CQS, explicit handlers/bus, constructor DI + logger) |
| **ARCH-PERSISTENCE** | `CS-PERSISTENCE` (AOT SQL/mappers, no `IQueryable`/`DbContext` leaks, SQL migrations) | `GO-PERSISTENCE` (explicit SQL/`sqlc`, no cursor leaks, SQL migrations) | `PY-PERSISTENCE` (explicit SQL/Core, no session leaks, SQL migrations) | `TS-PERSISTENCE` (explicit SQL/Kysely/Drizzle, no session leaks, SQL migrations) |
| **ARCH-STRICT** | `CS-TEST` (`Nullable`, warnings-as-errors) | `GO-TEST` (`gofmt`, `go vet`) | `PY-STRICT` (`ruff`, `mypy --strict` / `pyright` strict, no `Any`) | `TS-STRICT` (`strict`, `noUncheckedIndexedAccess`, no `any`) |
| **ARCH-FAILURE** | `CS-FAILURE` (`Nyssa.Results.Result<T>`) | `GO-FAILURE` (`(T, error)`, `%w` wrapping) | `PY-FAILURE` (`Result[T, E] = Ok[T] \| Err[E]`) | `TS-FAILURE` (discriminated-union `Result<T>`) |
| **ARCH-LOG** | `CS-LOG` | `GO-LOG` | `PY-LOG` | `TS-LOG` |
| **ARCH-LIFETIME** | `CS-CONSTRUCTION` & `CS-REGISTRATION` | `GO-LIFETIME` (`context.Context`) | `PY-LIFETIME` (context managers, explicit injection) | `TS-CONSTRUCTION` & `TS-REACT` (`AbortSignal`) |
| **ARCH-DOC** | `CS-DOC` | `GO-DOC` | `PY-DOC` | `TS-DOC` |
| **ARCH-TEST** | `CS-TEST` (xUnit) | `GO-TEST` (`testing`) | `PY-TEST` (`pytest` / `unittest`) | `TS-TEST` (Vitest) |
| **ARCH-REVIEW** | `CS-REVIEW` | `GO-REVIEW` | `PY-REVIEW` | `TS-REVIEW` |
