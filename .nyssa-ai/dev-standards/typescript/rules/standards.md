# TypeScript and React development rules

> [!IMPORTANT] Scope Directive
> Defines the mandatory architectural rules, multi-platform portability, Functional Core domain modeling, workflow orchestration, explicit persistence, single-responsibility headers, ASCII interface trees, strict type safety, operational logging, and testing contracts for TypeScript and React development in owned repositories. It inherits the [cross-language architectural rules](architecture-standards.md) and [common repository organization rules](repo-standards.md), governing feature-first organization, discriminated-union results, and explicit test isolation; it does NOT prescribe generic language tutorials or dictate external third-party library internals.

- **TS-FILE:** One concept/type per file, named for its primary type/export (or the `camelCase` stem of a `SCREAMING_SNAKE_CASE` module constant). Keep the concept's construction functions and behavior with it. A component's props describe the same concept and may stay beside the component; simple, pure feature-owned DTOs, readonly data interfaces, enums, and branded identifiers without behavioral methods may be grouped in a feature's `Types.ts` or `types.ts` file; framework-mandated file-router entrypoints (such as Next.js App Router `app/**/{page,layout,loading,error,global-error,not-found,template,default,route,opengraph-image,twitter-image,icon,apple-icon,sitemap,robots,manifest}.{tsx,ts}` and root `middleware.ts`, `proxy.ts`, `instrumentation.ts`) use their framework-required filenames, named `export default function` components, HTTP verb handlers (`GET`, `POST`, etc.), and static route segment metadata/config exports (`metadata`, `viewport`, `dynamic`, `revalidate`, `runtime`, `generateMetadata`, `generateStaticParams`); unrelated behavioral types or functions require separate files. Source files over 100 lines are discouraged (inspect files between 101 and 350 lines for mixed responsibilities), and files over 350 lines are prohibited. Use .tsx only for JSX.
- **TS-HEADER:** Every authored TypeScript/TSX file begins with a comment stating its Single Responsibility, followed by an ASCII tree of the public interface it exposes. Include exported types, functions, constants and public members, with parameter names for callable entries. Omit private implementation details; explicitly write `(none)` when nothing is exported. Keep the tree synchronized with code.
- **TS-STRUCTURE:** Follow the [common repository organization rules](repo-standards.md) (`REPO-ROOT`, `REPO-SCRATCH`, `REPO-CONFIG`, `REPO-DOCS`, `REPO-GOVERNANCE`, `REPO-TEST-LAYOUT`) and [cross-language architectural rules](architecture-standards.md). Organize production source under `src/` as a Feature-First Modular Monolith by feature, initially flat, with `camelCase` folders, and isolate tests under `test/unit/`, `test/use_case/`, and optional `test/e2e/` (Playwright) without co-mingling `*.test.ts` or `*.test.tsx` files in `src/`. Add progressive Hexagonal (`domain`, `application`, `infrastructure`, `api`, `ui`) layers inside a feature only when earned by complexity or multi-platform adapters, and use `.temp/` for local scratch and cache outputs. No `contracts`, `shared`, `utils`, `helpers`, `common`, `misc`, `types` or `models` catch-all folders (a feature-local `Types.ts` or `types.ts` file for pure DTOs is permitted, never a `types/` directory), and no `tmp`, `temp` or `scratch` folders. Public exports belong to their owning feature; expose only intended APIs at package entrypoints.
- **TS-BOUNDARY:** Domain/application do not import infrastructure, configuration or delivery. Consumers own collaborator contracts. Keep implementations private to their feature; provider contracts and required public data live at feature roots. A consumed package exposes a covering interface; data-only capabilities need no empty interface.
- **TS-PORTABILITY:** Keep `domain` and `application` modules 100% OS- and runtime-agnostic (portable across Node, browser, desktop/Electron/Tauri, and edge runtimes). Isolate Node `fs`/`path`/`child_process`, browser `window`/`localStorage`, and native bridge APIs behind narrow feature-owned interfaces implemented in `infrastructure`, `api`, or `ui`. Wire dependencies explicitly at the composition root; ban `reflect-metadata` decorator DI containers (`InversifyJS`, `TSyringe`, NestJS auto-scanning) and service locators.
- **TS-NAME:** Entity-first names (`UserRepositoryPostgres`, `emailFormatterJson`). Behavioral and data interfaces use `PascalCase` without an `I` prefix (`EmailFormatter`, not `IEmailFormatter`; only C# uses the `IInterface` convention). Functions use camelCase, components/types PascalCase, module constants SCREAMING_SNAKE_CASE, booleans assertion-like names and hooks use the use prefix.
- **TS-DATA:** Use readonly data interfaces, readonly collections and branded identifiers. Validate external data through named parsers; casts do not establish validity. Create changed values instead of mutating existing ones. Prefer string-literal unions for closed sets.
- **TS-DOMAIN:** Follow Functional Core / Imperative Shell domain modeling: represent domain entities and state as `readonly` records/interfaces and express business rules and state transitions as pure functions or methods returning `Result<T>` containing a new immutable object (`{ ...state, ... }`)—never mutating object properties in-place, performing I/O, or logging inside domain types. Action-taking handlers or services load state via narrow repository interfaces, invoke the pure transition, and persist the new record. Trivial pass-through CRUD workflows without domain invariants may operate directly on `readonly` DTOs in the handler/service. **Active Record** (TypeORM `BaseEntity`, Sequelize model instances with `.save()` / `.destroy()`, or lazy-loaded relation promises on domain models) is strictly prohibited.
- **TS-WORKFLOW:** Separate command workflows (validate, transition state, persist, and return `Result<T>`) from query workflows (Pragmatic CQS / Lightweight CQRS, reading directly into `readonly` projection DTOs when read shapes diverge from write models). Use tiered dispatch: direct constructor-injected service/handler calls for simple components or libraries, and an explicitly registered, type-safe Command/Query Bus (explicit handler map with middleware for logging/telemetry; no decorator/reflection scanning) for application workflows. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) must use explicit constructor Dependency Injection and inject a structured logger; pure value/DTO types remain dependency-free and logger-free. Default to current-state persistence (with explicit audit/outbox tables when needed), reserving Event Sourcing strictly for domains with an explicit ledger or replay requirement.
- **TS-PERSISTENCE:** Implement data access through explicit parameterized SQL (`pg`, `better-sqlite3`) or type-safe SQL builders (`Kysely`, `Drizzle` query builder) with explicit mapping into `readonly` DTOs/records. Ban Active Record, TypeORM/Hibernate-style lazy-loading proxies, and runtime reflection mappers (`class-transformer`). Never leak database clients, pools, transactions, or ORM query builders outside `infrastructure` adapters; command workflows own transaction boundaries explicitly. Manage schema changes exclusively through versioned, deterministic SQL migration files executed in production and in `test/use_case/` fixtures; ban runtime schema auto-sync (`synchronize: true`).
- **TS-STRICT:** Keep `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `verbatimModuleSyntax` enabled in every `tsconfig` that compiles owned TypeScript. These are mandatory compiler safeguards, comparable to treating warnings as build errors in C#; they are not optional migration targets and must not be disabled to reduce an error count. Repair the code or configuration that violates them. No `any`. Parse `unknown` at boundaries. Prefer narrowing; any non-null assertion needs a concrete documented justification.
- **TS-FAILURE:** Expected failure returns a discriminated-union Result. Translate dependency rejection at its boundary and preserve the original cause. An aborted operation rejects rather than returning a cancellation Result. Programmer errors throw Error objects. No floating promises. TS-LOG defines diagnostic ownership.
- **TS-LOG:** Robust logging is mandatory at owned operational boundaries. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) injects a structured logger via constructor DI, emitting `Info`/`Warn`/`Error` for operational boundary outcomes and `Debug`-level step telemetry (routed to diagnostic sinks such as Sentry or PostHog when debug mode is enabled). Emit structured, correlated outcomes with operation, severity, duration, safe diagnostic causes and deployed version. Expose actionable degradation before failure, including relevant retries, latency and fallback use. Assign one owner to each terminal outcome; keep pure domain logic and `readonly` DTOs quiet. Exclude secrets and sensitive payloads, bound logging cost, and contain sink failures without changing business results. Test emitted records and document how they support detection, diagnosis and verification of a fix. Follow the [logging contract](../references/typescript/logging.md); a logger call alone is not conformance.
- **TS-CONSTRUCTION:** Inject storage, transport, time, randomness, and loggers through constructors (for action-taking classes), parameters, or composition. Avoid mutable module singletons, service locators and import-time effects. I/O accepts and honors AbortSignal.
- **TS-REACT:** Named function components, destructured props and top-level unconditional hooks. Complete effect dependencies and cleanup. Rendering delegates domain decisions to application functions; fetching belongs in a hook/loader. No class components or React.FC.
- **TS-DOC:** TSDoc for exported declarations and members, including meaningful failure, lifetime and ownership contracts.
- **TS-TEST:** Use Vitest with subject_scenario_expected names and it.each for multiple examples of one behavior. Test runtime behavior, strict emitted types and meaningful UI interactions. Maintain fast unit tests in `test/unit/`, complete public caller/backend workflow tests in `test/use_case/` (using real Docker-hosted or local database dependencies for infrastructure-backed behavior), and optional full-stack browser end-to-end tests (such as Playwright) in `test/e2e/`. Tests are executable documentation: use the simplest idiomatic style, direct setup/actions/assertions and only patterns justified by a concrete need (KISS). Hide infrastructure lifecycle in fixtures while keeping public usage and business expectations visible. Follow the [testing contract](../references/typescript/testing.md), including isolation, cleanup, logging evidence and explicit local execution; passing compilation or starting a container is insufficient.

- **TS-REVIEW:** Use the [code-smell and anti-pattern catalog](../references/typescript/code-smells.md) for relevant changed code and tests. Distinguish explicit rule violations from smells needing investigation. Every finding needs source evidence, an applicable rule or demonstrated problem, a concrete consequence and the smallest correction. Preserve justified patterns and simple code; do not refactor from names, line counts or smell labels alone.

## Design decisions (review required)

- **SOLID-S:** Give each component one coherent responsibility. Separate business policy from delivery and infrastructure when their reasons for changing differ.
- **SOLID-O:** Extend established variation through another implementation without changing the stable workflow. Introduce a seam only for real variation, external I/O, or an actual consumer boundary.
- **SOLID-L:** Every implementation honors the complete contract, including failure, ownership, cancellation and side effects. Run the same behavioral contract against interchangeable implementations.
- **SOLID-I:** Keep contracts specific to their consumers. No dummy operations, fabricated success, silent no-ops or unsupported members.
- **SOLID-D:** Core policy owns its collaborator abstractions. Adapters implement them; composition supplies implementations. Keep vendor, transport and persistence types outside core contracts.
- **REPO-FEATURES:** Prefer aligning feature folders under `src/` (and mirrored suites under `test/unit/` and `test/use_case/`) with cohesive `plan-product` Feature Groups (`F-gg` in `docs/features.md`) or domain concepts (`C-nn` in `docs/concepts/`) rather than creating a separate top-level folder per individual `F-gg.nn` feature number. Keep subordinate features within their owning feature-group folder, starting flat.
- Use dependency injection, repository, adapter, strategy, decorator, factory, builder, observer or covering interface only when the task justifies that particular pattern. A simple change can need no new pattern.
- Make resource ownership explicit. A component disposes what it owns, never what it borrows. Inject time, randomness and external systems when core behavior depends on them.
- Prefer JSON-RPC 2.0 over HTTPS for new request/response network APIs unless explicit compatibility requirements dictate otherwise. Keep protocol handling separate from business invariants; check those invariants for non-network callers too.

## Observable examples and tests

Samples must run, expose actual results, show a meaningful expected failure, and test those observations through the public surface. A compiling example is not proof of behavior. Explain why the design applies and when a simpler design is enough. Keep tests deterministic and resources isolated. Integration tests must exercise the technologies actually claimed; an in-memory provider does not prove database persistence. Library tutorial tests show public setup and the complete caller workflow, with one visible Arrange / Act / Assert sequence. Contract tests must exercise every interchangeable implementation.

## Scope and precedence

Explicit user and repository requirements take precedence. Record an exception with its scope and reason; do not silently disable a check. Apply rules to owned code; respect upstream compatibility and generated-code conventions. These are Jeremy Maynor's preferences, not claims of universal language practice. A passing check covers only the checks listed in the package README. SOLID judgment, useful comments, conceptual cohesion and full correctness still require review.
