# C# development rules

> [!IMPORTANT] Scope Directive
> Defines the mandatory architectural rules, Native AOT portability, Functional Core domain modeling, workflow orchestration, explicit persistence, type placement conventions, error results, operational logging, and testing contracts for C# / .NET development in owned repositories. It inherits the [cross-language architectural rules](architecture-standards.md) and [common repository organization rules](repo-standards.md), governing concept boundaries, class sealing, immutability, and explicit failure flows; it does NOT prescribe generic framework tutorials or dictate external third-party library internals.

- **CS-FILE:** Give each class or interface its own file, named after the type. Numerous, closely related, simple DTOs or enums may share a clearly named file within one namespace. Records follow the same placement rule. Grouping requires an explicit per-file exception and reason; behavior-bearing classes and interfaces cannot use it. Source files over 100 lines are discouraged (inspect files between 101 and 350 lines for mixed responsibilities), and files over 350 lines are prohibited.
- **CS-STRUCTURE:** Follow the [common repository organization rules](repo-standards.md) (`REPO-ROOT`, `REPO-SCRATCH`, `REPO-CONFIG`, `REPO-DOCS`, `REPO-GOVERNANCE`, `REPO-TEST-LAYOUT`) and [cross-language architectural rules](architecture-standards.md). Organize production source under `src/` as a Feature-First Modular Monolith by feature and isolate tests under `test/unit/` and `test/use_case/` without co-mingling `*Tests.cs` files in `src/`. Start flat; add progressive Hexagonal (`Domain`, `Application`, `Infrastructure`) and delivery folders inside a feature only when justified by complexity or multi-platform adapters. Use `PascalCase` folders, `.csproj` names, and matching namespaces, with shared build settings in `Directory.Build.props` and `.temp/` for local scratch outputs. No `contracts`, `shared`, `utils`, `helpers`, `common`, `misc`, `types` or `models` catch-all folders, and no `tmp`, `temp` or `scratch` folders in owned source.
- **CS-BOUNDARY:** Domain has no Application, Infrastructure, Configuration or delivery dependencies; Application has no Infrastructure, Configuration or delivery dependencies. Collaborating features use their root contracts, never another feature's implementation. A consumed library exposes its covering interface; provider contracts and public data belong to the owning feature, implementations to Client or the owning feature. Data-only capabilities need no empty interface.
- **CS-PORTABILITY:** Owned C# code must be multi-platform and Native AOT / trim-compatible (`<IsAotCompatible>true</IsAotCompatible>` / `<EnableTrimAnalyzer>true</EnableTrimAnalyzer>`). Keep `Domain` and `Application` 100% OS- and platform-agnostic, isolating OS-specific paths, native interop, registry/keychain access, and UI/transport mechanics behind narrow feature-owned interfaces in `Infrastructure` or delivery adapters. Wire dependencies explicitly at the composition root or via compile-time source generators (`System.Text.Json` `JsonSerializerContext`, compile-time DI); ban runtime assembly scanning (`Scrutor`, `Assembly.GetTypes()`), reflection-based auto-registration, `Reflection.Emit`, dynamic proxy generation, and service locators.
- **CS-NAME:** Entity-first names (UserRepositoryPostgres). I-prefixed interfaces at all visibilities (only C# uses the `IInterface` convention), explicit access modifiers, PascalCase members, camelCase parameters, underscore-prefixed private fields, Async suffixes on asynchronous methods, and assertion-like Boolean names.
- **CS-DATA:** Data-carrying types are expanded-body records. Use required/init for caller-initialized data, private construction and getters for validated values, typed domain identifiers, and immutable or defensively copied collections. No positional records or primary constructors. Keep I/O and orchestration out of data types.
- **CS-DOMAIN:** Follow Functional Core / Imperative Shell domain modeling: model domain state as immutable expanded-body `record` types and express business rules and state transitions as pure methods or functions returning `Result<T>` with a new record instance (`with { ... }`)—never mutating entity state in-place, performing I/O, or logging inside domain types. Action-taking handlers or services load state via narrow repository interfaces, invoke the pure transition, and persist the resulting record. Trivial pass-through CRUD workflows without domain invariants may operate directly on immutable DTO records in the handler/service. **Active Record** (domain objects holding a `DbContext`/connection or exposing `.SaveAsync()`/`.UpdateAsync()`/`.DeleteAsync()` persistence methods) is strictly prohibited.
- **CS-WORKFLOW:** Separate command workflows (validate, transition state, persist, and return `Result`) from query workflows (Pragmatic CQS / Lightweight CQRS, reading directly into immutable projection records when read shapes diverge from write models). Use tiered dispatch: direct constructor-injected service/handler calls for simple components or libraries, and an AOT-safe, explicitly registered Command/Query Bus (static generic dispatch with pipeline middleware for logging/telemetry; no runtime reflection or assembly scanning like reflection-based `MediatR`) for application workflows. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) must use explicit constructor Dependency Injection and inject a structured `ILogger`; pure value/DTO records remain dependency-free and logger-free. Default to current-state persistence (with explicit audit/outbox tables when needed), reserving Event Sourcing strictly for domains with an explicit ledger or replay requirement.
- **CS-PERSISTENCE:** Implement data access through explicit parameterized SQL (`DbDataReader`, `NpgsqlDataSource`, `Dapper.AOT`) or AOT-verified query builders with explicit or compile-time source-generated mapping (`Riok.Mapperly` or hand-written factory methods) into immutable records. Ban Active Record, EF Core lazy-loading proxies, implicit change-tracker side effects across layers, and runtime reflection object mappers (`AutoMapper`). Never leak `IQueryable<T>`, `DbContext`, `DbConnection`, or `DbTransaction` outside `Infrastructure` adapters; command handlers or explicit unit-of-work adapters own transaction boundaries. Manage schema changes exclusively through versioned, deterministic SQL migration files executed in production and in `test/use_case/` fixtures; ban runtime schema auto-generation (`Database.EnsureCreated()`).
- **CS-FAILURE:** Fallible operations return Nyssa.Results Result/Result<T>, or Task<Result...>. Use the actual canonical API: Guard.Against and Then for validation, Then/Transform/Resolve for composition. Initialization alone may terminate guards with ThrowIfError. Narrow adapter boundaries translate recoverable exceptions and cancellation into the owned error model, preserve internal causes and avoid exposing secrets. Do not catch fatal process conditions. CS-LOG defines diagnostic ownership.
- **CS-LOG:** Robust logging is mandatory at owned operational boundaries. Every action-taking class (Command/Query Handlers, Application Services, Infrastructure Repositories/Adapters) injects a structured logger via constructor DI, emitting `Info`/`Warn`/`Error` for operational boundary outcomes and `Debug`-level step telemetry (routed to diagnostic sinks such as Sentry or PostHog when debug mode is enabled). Emit structured, correlated outcomes with operation, severity, duration, safe diagnostic causes and deployed version. Expose actionable degradation before failure, including relevant retries, latency and fallback use. Assign one owner to each terminal outcome; keep pure domain logic and DTO records quiet. Exclude secrets and sensitive payloads, bound logging cost, and contain sink failures without changing business results. Test emitted records and document how they support detection, diagnosis and verification of a fix. Follow the [logging contract](../references/csharp/logging.md); a logger call alone is not conformance.
- **CS-CONSTRUCTION:** Inject dependencies through constructors; seal classes by default. Honor CancellationToken for I/O and document ownership. Reuse canonical Nyssa capabilities rather than creating lookalikes.
- **CS-REGISTRATION:** For library DI setup, use an immutable configuration record and one validating DTO master overload. Configuration-factory and stored-configuration routes prepare a snapshot and delegate; call the factory once. Validate and prepare before changing registrations; use deferred construction and DI disposal. Never BuildServiceProvider during registration. Borrow stored configuration and await loading before host construction.
- **CS-DOC:** XML-document public types and members, including failure, cancellation and ownership contracts. Use generated-documentation diagnostics. C# has no ASCII header inventory requirement.
- **CS-TEST:** Use xUnit with Method_Scenario_Expected names and Theory for multiple examples of one behavior. Enable nullable analysis and warnings-as-errors. Maintain fast unit tests and complete public use-case tests, using real Docker-hosted dependencies for infrastructure-backed behavior. Tests are executable documentation: use the simplest idiomatic style, direct setup/actions/assertions and only patterns justified by a concrete need (KISS). Hide infrastructure lifecycle in fixtures while keeping public usage and business expectations visible. Follow the [testing contract](../references/csharp/testing.md), including isolation, cleanup, logging evidence and explicit local execution; passing compilation or starting a container is insufficient.

- **CS-REVIEW:** Use the [code-smell and anti-pattern catalog](../references/csharp/code-smells.md) for relevant changed code and tests. Distinguish explicit rule violations from smells needing investigation. Every finding needs source evidence, an applicable rule or demonstrated problem, a concrete consequence and the smallest correction. Preserve justified patterns and simple code; do not refactor from names, line counts or smell labels alone.

## Design decisions (review required)

- **SOLID-S:** Give each component one coherent responsibility. Separate business policy from delivery and infrastructure when their reasons for changing differ.
- **SOLID-O:** Extend established variation through another implementation without changing the stable workflow. Introduce a seam only for real variation, external I/O, or an actual consumer boundary.
- **SOLID-L:** Every implementation honors the complete contract, including failure, ownership, cancellation and side effects. Run the same behavioral contract against interchangeable implementations.
- **SOLID-I:** Keep contracts specific to their consumers. No dummy operations, fabricated success, silent no-ops or unsupported members.
- **SOLID-D:** Core policy owns its collaborator abstractions. Adapters implement them; composition supplies implementations. Keep vendor, transport and persistence types outside core contracts.
- **REPO-FEATURES:** Prefer aligning feature folders under `src/` (and mirrored suites under `test/unit/` and `test/use_case/`) with cohesive `plan-product` Feature Groups (`F-gg` in `docs/features.md`) or domain concepts (`C-nn` in `docs/concepts/`) rather than creating a separate top-level folder per individual `F-gg.nn` feature number. Keep subordinate features within their owning feature-group folder, starting flat.
- Use dependency injection, repository, adapter, strategy, decorator, factory, builder, observer or covering interface only when the task justifies that particular pattern. A simple change can need no new pattern.
- Make resource ownership explicit. A component disposes what it owns, never what it borrows. Inject time, randomness and external systems when core behavior depends on them.
- Prefer JSON-RPC 2.0 over HTTPS for new request/response network APIs unless explicit compatibility requirements dictate otherwise. Keep protocol handling separate from business invariants; check those invariants for non-network callers too.

## Observable examples and tests

Samples must run, expose actual results, show a meaningful expected failure, and test those observations through the public surface. A compiling example is not proof of behavior. Explain why the design applies and when a simpler design is enough. Keep tests deterministic and resources isolated. Integration tests must exercise the technologies actually claimed; an in-memory provider does not prove database persistence. Library tutorial tests show public setup and the complete caller workflow, with one visible Arrange / Act / Assert sequence. Contract tests must exercise every interchangeable implementation.

## Scope and precedence

Explicit user and repository requirements take precedence. Record an exception with its scope and reason; do not silently disable a check. Apply rules to owned code; respect upstream compatibility and generated-code conventions. These are Jeremy Maynor's preferences, not claims of universal language practice. A passing check covers only the checks listed in the package README. SOLID judgment, useful comments, conceptual cohesion and full correctness still require review.
